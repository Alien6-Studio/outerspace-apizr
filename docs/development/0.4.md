# Build and qualify Apizr from source

For the release overview, read [0.4.0 notes](../releases/0.4.0.md).
This page retains the complete development installation and delivery walkthrough.

For installation without building Apizr, use [Install Apizr](../getting-started/install.md).

## What is available

| Step | Implemented interface and detailed reference |
| --- | --- |
| Choose sources | Local directory, [public Git HTTPS](../reference/git-sources.md), or [private Git with an explicit SSH agent and known_hosts](../reference/git-ssh.md) |
| Analyze and select | [Readiness](../getting-started/user-guide/repository-readiness.md) and explicit [exposure policy](../getting-started/user-guide/exposure.md), shared by the CLI and [Python compiler API](../reference/compiler-api.md) |
| Configure and generate | Explicit [apizr.toml](../getting-started/user-guide/project.md), then REST/MCP repository bundles |
| Analyze from an MCP client | Optional [outerspace-apizr-mcp local stdio server](../reference/apizr-mcp-server.md): analysis, readiness and explicit planning, read-only |
| Declare project plugins | [Explicit user preferences and deterministic plugin locks](../reference/project-plugin-locks.md), with artifact/inventory checks and explicit offline additive `plugins sync` and controlled `plugins update` |
| Choose official plugins | [Versioned catalog and explicit MCP, OCI and delivery profiles](../reference/plugin-catalog.md), with static export for offline sync |
| Prepare optional tools | [Install, list, enable, run, disable and uninstall isolated plugins](../reference/local-extensions.md); local/HTTPS wheels, locked local dependencies and resumable removal of inactive, unused versions |
| Authorize image operations | [Explicit operator grants](../reference/operator-policy.md) for exact build targets, signing identities/authorities and publication repositories |
| Package and deliver | [outerspace-apizr-oci build and push](../reference/oci-service-plugin.md): service image, immutable image identity, verified registry digest |
| Sign delivery | [outerspace-apizr-attest attest and verify](../reference/attest-delivery-plugin.md): signed, RFC 3161 timestamped delivery receipt |
| Transport proof | [publish, discover and fetch](../reference/attest-oci-artifacts.md): OCI referrers, explicit proof digest, independent offline verification |

Git acquisition and the compiler belong to the minimal core. OCI, Attest and
Apizr's local MCP server are separately installed optional plugins. A generated
**business MCP server** exposes selected functions; **Apizr itself as an MCP
server** provides local stdio analysis and planning only. Postman synchronization,
user-facing CI catalogue integrations and automatic plugin
updates are not implemented. Existing repository CI jobs are development
validation, not those user integrations. Distribution qualification experiments
do not constitute released 0.4 packages or catalogue admission.

## Install a development wheel

These commands are executable as written on macOS/Linux with Git, uv and
Python 3.11–3.14 already installed. Start in an empty working directory.
**Preparation may download** the source, build backend and Pydantic dependency
closure. It does not install optional application adapters or plugins.

```sh
git clone https://github.com/Alien6-Studio/outerspace-apizr.git apizr-source
cd apizr-source
git switch --detach origin/release/0.4.1
source_commit=$(git rev-parse HEAD)
work=$(mktemp -d)
work=$(cd "$work" && pwd -P)
printf '%s\n' "$source_commit" > "$work/source-commit.txt"
uv build --wheel --out-dir "$work/dist"
cp -R examples/project-config "$work/project-config"
cd "$work"
uv venv --no-python-downloads --python python3 core
uv pip install --python core/bin/python dist/outerspace_apizr-0.4.1rc1-py3-none-any.whl
core/bin/apizr --version
cat source-commit.txt
```

The source revision is frozen at clone time; retain `source-commit.txt` with the
wheel and its SHA-256. For an independently selected revision, replace
`origin/release/0.4.1` with that full commit before building. The core and OCI/Attest/MCP plugin wheels now declare **0.4.1rc1**. These are
**verification builds from that commit**. Their version alone does not prove
that they match the published package bytes.
`apizr --version` alone cannot distinguish them. Build all plugin wheels from the
same checkout; use separate core environments and plugin stores for stable and
development work. The site [build information](https://apizr.outerspace.sh/build-info.json) identifies
its documentation source, not the source of a wheel on your machine.

### Generate locally, outside the checkout

The copied example includes `src/calculator.py`, both explicit JSON policies and
`apizr.toml`. From `$work`, after the installation above:

<!-- smoke:development -->
```sh
core/bin/python - <<'PYTHON'
import json
from pathlib import Path
root = str(Path("project-config").resolve())
Path("operator.json").write_text(json.dumps({"schema":"apizr.operator-policy/v1","grants":[{"adapter":"repository","operation":"analyze","target":{"kind":"local","root":root},"permissions":["source.analyze"]}]}))
PYTHON
core/bin/apizr readiness --project project-config/apizr.toml --operator-policy operator.json --report > readiness.json
core/bin/apizr expose plan --project project-config/apizr.toml --operator-policy operator.json --plan > plan.json
core/bin/apizr expose build rest --project project-config/apizr.toml --operator-policy operator.json --output-dir build/rest
core/bin/apizr expose build mcp --project project-config/apizr.toml --operator-policy operator.json --output-dir build/mcp
```
<!-- /smoke:development -->

All four commands succeed: `calculator.add` is ready and explicitly selected;
both bundles contain that public capability. Generation is static and offline:
no import of the project, dependency installation, plugin or Docker invocation.
The [Git example](../reference/git-sources.md#one-explicit-revision) prepares the
same two local policy files and generates from an immutable remote commit instead.
Git fetch accesses the chosen server; it does not download application dependencies.
SSH additionally requires the explicitly prepared agent and host trust file.

## Reproduce the complete delivery in a disposable environment

The existing integration script supplies the complete preparation that a real
registry deployment otherwise requires: two disposable Linux Docker daemons,
an authenticated HTTPS registry and explicit test CA, a local RFC 3161 authority,
a test signing key, independent trust, pinned Attest/ORAS binaries, locked wheels,
and fixture source. It builds and installs the core and plugins **outside the
checkout** and exercises real REST/MCP services without the original sources.

Use a Docker host that permits privileged disposable containers and Linux amd64
images (with emulation already configured on arm64), Python 3.11+ and an installed
Docker CLI. Return to the selected `apizr-source` checkout. This command is
executable as written; the output directory is new:

```sh
proof_parent=$(mktemp -d)
python3 scripts/smoke_oci_registry.py --artifacts --output "$proof_parent/proof"
cat "$proof_parent/proof/outcome.json"
cat "$proof_parent/proof/artifact-fetch-result.json"
```

**This script downloads preparation dependencies/images and publishes test images
and proofs, exclusively into its disposable registry.** It does not publish to
Docker Hub, Trunx or a production registry, change machine trust or use release
signing keys. It removes its named containers, volume and network; downloaded
base images/build caches may remain. It retains public results, refusal cases,
locks and test logs. Expect `outcome.json` to contain `{"exit_code": 0}` and the
fetch evidence to confirm byte-identical proof files and an unchanged core.
Read the [integration proof contract](../reference/attest-oci-artifacts.md#reproduce-the-installed-package-proof)
for the independent, read-only consumer and networkless verification checks.

The script reuses this sequence rather than introducing another installer or
build chain:

**local/Git snapshot → readiness and explicit selection → REST/MCP bundle →
service image → verified OCI push → signed and timestamped delivery receipt →
OCI proof publication → untrusted discovery → explicit fetch → offline verify.**

## Keep results and verify operation states

For a deployment you control, use the complete JSON request examples on the
[OCI](../reference/oci-service-plugin.md) and [Attest](../reference/attest-delivery-plugin.md)
pages. Their `registry.example`, digests, signer identities and absolute paths
are **values to replace**, not executable production defaults. Prepare the
reviewed wheels, Docker/Buildx, authentication, trust and output parents first.
The following commands assume `core/bin/apizr`, `$work/plugins`, `build.json`
and `push.json` prepared as on those pages. Prepare an explicit
[operator.json](../reference/operator-policy.md) with a matching build target and
both `image.build` and `registry.read` before starting. Signing and publication
need separate grants. **Push actually publishes.**

```sh
core/bin/apizr plugins run outerspace-apizr-oci build --arguments build.json \
  --operator-policy operator.json \
  --plugins-dir "$work/plugins" --timeout-ms 360000 > build-response.json
core/bin/python - <<'PY'
import json
from pathlib import Path
response = json.loads(Path("build-response.json").read_text())
assert response["status"] == "ok"
result = response["result"]
assert result["schema"] == "apizr.oci-build-result/v1"
assert result["published"] is False
Path("build-result.json").write_text(json.dumps(result))
PY
```

Fill `push.json` using **that result's** `image_id`, `platform` and
`inputs_sha256` and, for 0.4.1 builds, its complete `delivery_manifest` object,
plus your explicit destination, Docker and authentication
parameters. Do not select a possibly moved local tag instead of `image_id`.
Prepare [operator.json](../reference/operator-policy.md) for the exact installed
build and repository; both registry read and publish grants are required.

```sh
core/bin/apizr plugins run outerspace-apizr-oci push --arguments push.json \
  --operator-policy operator.json --plugins-dir "$work/plugins" --timeout-ms 360000 > push-response.json
core/bin/python - <<'PY'
import json
from pathlib import Path
response = json.loads(Path("push-response.json").read_text())
assert response["status"] == "ok"
result = response["result"]
assert result["schema"] == "apizr.oci-push-result/v1"
assert result["published"] is True
assert result["digest_reference"].endswith("@" + result["manifest_digest"])
Path("push-result.json").write_text(json.dumps(result))
PY
```

Pass the **absolute paths to these two result files**, not the protocol envelopes,
as `build_result` and `push_result` in `attest.json`. Its `expected_reference`
comes from `digest_reference`; the expected signer and trust come from your
independent selection. Keep the local immutable image until `attest` completes.
Then follow the proof publication page using the exported proof directory.
The consumer chooses an explicit artifact digest; discovery never chooses for it.

| Operation | Required success evidence |
| --- | --- |
| `build` | `apizr.oci-build-result/v1`, checked image/platform/inputs, `published:false` |
| `push` | `apizr.oci-push-result/v1`, `published:true`, verified manifest/config identities and digest reference |
| `attest` / `verify` | `apizr.attest-delivery-result/v1`, expected identity, all five native checks pass, no warnings/skips; `receipt_published:false` |
| `publish` | `apizr.published-proof/v1`, `state:"verified"`, `receipt_published:true`, non-null artifact identity |
| `discover` | `apizr.discovered-proofs/v1`, `complete:true`; candidates remain `verified:false`, not selected or trusted |
| `fetch` | `apizr.fetched-proof/v1`, exact chosen artifact/image identities, verified exported proof and five native checks |

A returned JSON object or exit zero alone is insufficient. Proof publication can
return `state:"remote_state_unconfirmed"`: that is **not confirmed success**.
Image push can fail after transfer; the core redacts plugin errors. Interruption
never proves rollback. Inspect remote state before retrying; nothing deletes
remote artifacts automatically. Offline `verify` establishes receipt integrity,
signer and independently configured trust, not current registry availability.

## Boundaries that still apply

- The OCI plugin accepts direct repository REST/MCP bundles and the supported
  server closure plus explicitly declared application dependencies and resources.
  See [application inputs](../getting-started/user-guide/project.md#application-dependencies-and-resources-041-development).
  A **service image** is different from the **governed execution worker image**.
- Core, plugin and generated application dependencies live in different
  environments. Plugin local/locked installation is offline; HTTPS plugin
  acquisition is not. External tools are explicitly prepared, never silently
  downloaded during invocation. Docker base resolution may still access a registry.
- Attest proves **verified delivery**, not a build supervised by Attest, SLSA or
  reproducible layers. Hash integrity is not author trust or independent signer trust.
- Proof transport requires the documented single-image SHA-256 OCI profile and
  OCI 1.1 referrers API in the same repository, without tag fallback or multiarch.
  Docker Hub and Trunx have **not** been qualified by the disposable fixture.
- The compiler does not execute source during analysis. Running generated services
  and trusted plugins does execute code; activation is not a sandbox. Process
  cleanup cannot undo daemon work or a completed remote upload.

Release preparation and remaining qualification are still separate from these
integrated capabilities. An empty issue list would not establish 0.4 completeness.

MCP qualification is tracked in
[#142](https://github.com/Alien6-Studio/outerspace-apizr/issues/142). The installed
analysis plugin and generated-business-server recovery run in independent CI
jobs. Both, plus general CI, must pass on the same commit; see the
[qualification instructions](../reference/apizr-mcp-server.md#qualification-evidence).
Historical timeout evidence is retained; functional recovery and short execution
deadlines have separate tests, without changing production defaults.

Configuration and artifact locking are tracked in [#146](https://github.com/Alien6-Studio/outerspace-apizr/issues/146). Additive synchronization is tracked in [#148](https://github.com/Alien6-Studio/outerspace-apizr/issues/148). Controlled updates are tracked in [#150](https://github.com/Alien6-Studio/outerspace-apizr/issues/150). Safe removal is tracked in [#159](https://github.com/Alien6-Studio/outerspace-apizr/issues/159); the official catalog and profiles in [#161](https://github.com/Alien6-Studio/outerspace-apizr/issues/161). Operator grants now cover Git acquisition, source analysis, image construction, signing and publication independently. User preferences do not grant permissions.

## Operator authorization by operation

Publication admission covers `outerspace-apizr-oci push` and `outerspace-apizr-attest publish`;
delivery signing admission covers `outerspace-apizr-attest attest`.
Git acquisition and repository analysis require separate explicit grants.
Image construction has its own grant too. Existing technical controls remain;
no MCP publication is added. Qualification of the exact release candidate
remains necessary.

### Explicit authorization for delivery signing

Managed `outerspace-apizr-attest attest` now requires an explicit operator signing rule,
separate from publication. It binds the installed plugin and locked dependencies,
repository, key reference/identity, expected signer and TSA, with registry read,
receipt signing and timestamp permissions. Refusals occur before plugin execution
or key/credential access. [Policy and complete example](../reference/operator-policy.md#authorize-signing-separately).
Offline verification and publication of an existing proof need no private key.
Repository analysis has a separate `source.analyze` grant, described below.

### Explicit authorization for image construction

Managed `outerspace-apizr-oci build` requires its own operator grant, bound to the installed
plugin/closure, pinned base image, interface/platform, input references, Docker
parameters and local tag. Both `image.build` and `registry.read` are required;
signing and publication stay independently authorized. See the
[build rule and complete example](../reference/operator-policy.md#authorize-an-image-build).
The builder still validates and snapshots actual bytes, generates its Dockerfile
and confirms the image with `published:false`. Base resolution may access the
registry; `--network=none` does not isolate all daemon traffic. This change does
not govern bundle generation (`apizr expose build`) or execution workers.

### Explicit authorization for remote Git acquisition

The four readiness/exposure commands using `--git` and the public
`acquire_snapshot` API now require a separate `git.fetch` operator grant before
Git/SSH execution, trust-file reads, network/agent access or workspace creation.
Git remains part of the minimal core. [Complete HTTPS and SSH policies](../reference/operator-policy.md#authorize-a-git-source)
bind the exact repository/transport, revision, subdirectory and trust references.
The [HTTPS](../reference/git-sources.md) and [SSH](../reference/git-ssh.md) examples
provide `--operator-policy operator.json` and use the same policy in Python.

Installed-wheel proofs first verify refusals before effects, then compare all four
commands and direct API generation with local sources against real disposable
HTTPS/SSH servers. Snapshots are cleaned while generated bundles remain usable;
OCI/Attest fixture acquisition supplies its own explicit Git grant. Trust-file
references do not pin bytes; branches authorize a requested name, and `subdir`
is not a restriction on transferred repository objects. Analysis admission separately requires `source.analyze`; acquisition alone
does not grant access through the managed compiler.

### Explicit authorization for repository analysis

The shared gate protects filesystem discovery for scan, graph, readiness,
exposure and bundle preparation in CLI/Python and the local MCP server.
MCP snapshots authority across exec/workers; policy changes require a restart.
[Complete local/Git policies](../reference/operator-policy.md#authorize-repository-analysis).
[Issue #173](https://github.com/Alien6-Studio/outerspace-apizr/issues/173) tracks
implementation and qualification. Its PR checks qualify the exact commit, not a
released package. Retained rendering and in-memory primitives keep their contracts.

## Delivery scope and explicit deferrals

The published coordinated baseline is **0.4.0rc1**. Development next targets
`release/0.4.1`, through short-lived feature PRs. RC tags `v0.4.1rc1`, `v0.4.1rc2`,
etc. identify qualified candidates; final `v0.4.1` precedes protected reintegration
into `master`. Only then create `release/0.4.2`. There will be no new final 0.4.0.
The first functional increment adds explicit application inputs and advances all
four development distributions to **0.4.1rc1**. This version identifies development
artifacts; it creates no RC tag and authorizes no publication.

| Version | Delivery scope |
| --- | --- |
| [0.4.0](https://github.com/Alien6-Studio/outerspace-apizr/milestone/8) | Integrated foundation; Git/analysis authorization; official distributions; migration; qualification and verified publication |
| [0.4.1](https://github.com/Alien6-Studio/outerspace-apizr/milestone/10) | Application dependencies/resources; transversal manifest; multiple destinations; mandatory proof; Docker Hub/Trunx qualification |
| [0.4.2](https://github.com/Alien6-Studio/outerspace-apizr/milestone/11) | Delivery from MCP; Postman export/synchronization; GitHub/GitLab integrations; initialization, diagnostics, completion; Homebrew tap |

These are explicit deferrals, not abandoned acceptance criteria. Completed work
stays closed; the 0.4.0rc1 scope includes none of those deferred features.
Third-party catalogue admission remains separate from product release.

The coordinated **0.4.0rc1** packages are published with retained matrix and
installed-package qualification. See the [release record](../releases/0.4.0.md#publication-status)
for exact source, public archives and verification. Contributors should keep
future release-line candidate validation separate from passing baseline/documentation checks.

## Official distribution images remain deferred

The CI worker and registry-proof images are disposable test fixtures. They are
not official Apizr images offered for installation. Distribution of official
Apizr images is deferred to subsequent deliveries and remains unfinished; no
public registry destination is claimed. This is separate from the qualified
OCI plugin that builds and publishes a user's service images.
